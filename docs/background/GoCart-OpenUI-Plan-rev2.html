GoCart on OpenUI

Rebuild a normal web app so its pages are OpenUI layouts. Users can then add and change cards on their own screens by asking, and nobody has to edit code for each request.

12 Oct 2026 Test app: GoCart (open-source shop, used as the test subject) Reference: ZoomInfo Open-UI POC Draft for discussion

What changed in revision 2. Tools are defined once in a tool registry inside the app; MCP becomes an optional adapter. Users no longer get a full copy of the page; their cards and changes are separate rows. Generated cards get a dry run before saving. The plan now builds one complete demo slice first and lists what must be finished before real customer data is used.

1 · Goal

The problem and what we want to build

The problem

Every user wants their screens a little different. A seller wants "orders waiting more than 2 days". An admin wants "revenue per store as a chart". Today each of these is a feature request that waits for a developer. SaaS teams will not rewrite legacy code for each user.

What we want

A floating Ask button. The user types what they want and a working card appears on the page. They can move it, pin it or delete it. It is still there tomorrow, showing tomorrow's numbers.

Why GoCart

GoCart is an open-source shop (storefront, seller dashboard, admin panel) that we use only as a test subject. If the method works on GoCart, it can be applied to other apps.

The one rule

The AI proposes a screen. The server decides what is valid, what the user may see, and what actually runs. The AI never sees the data; each card fetches its own data every time it opens.

2 · Architecture

One app, one tool registry, one database

Everything runs inside the GoCart Next.js app. MCP is an adapter we can add later for outside agents; it is not in the path of page loads.

│ Page shell (React): nav, login, payment, │
│ image upload                             │
│  ├─ Role page layout     (OpenUI Renderer)│

│  ├─ Ask button                            │
│  └─ Query cache (keyed by user) +         │◀─ refetch when the date range

│ Session cookie → ctx {userId, storeId, role}                      │

A tool is defined once

defineTool({
  name: "get_store_orders",
  roles: ["seller"],
  input: z.object({
    olderThanDays: z.number().int().min(0).max(90),
  }).strict(),
  output: z.object({ orders: z.array(Order) }),
  reads: ["orders"],
  timeoutMs: 3000, maxRows: 500,
  handler: (ctx, args) =>
    repo.orders.forStore(ctx.storeId, args),
})

Why this shape

  • The page API, the AI's tool list and a future MCP server come from the same definition, so they cannot drift apart.
  • ctx comes only from the session. It is never part of args, so there is nothing to strip.
  • .strict() rejects any field the schema does not list.
  • Handlers only use store-scoped repository functions. No raw queries in handlers.
  • Every tool has a timeout and a row limit.
3 · How it works

From a question to a live card

3.1 Creating a card (/api/ask)

User

Asks with the Ask button

"Show orders waiting more than 2 days."

Server · prompt

The AI gets the question, components and allowed tools

A trimmed component list and the schemas of only the read tools this role may use. No data rows.

LLM

Writes a layout in OpenUI Lang

One complete response, not streamed, so the card is checked and saved as a whole.

Server · parse and validate

The app checks the layout itself

Registered components only. Every tool exists and its args match the schema. Every binding path exists in the tool's output schema. No Mutation. No hard-coded values inside data components (Table, Chart, Stat). If it fails, the errors go back to the model once for a repair.

Server · dry run

The card's queries run once as this user

The rows are used only to check that bindings resolve. They are never sent to the model. See the table below for what each result means.

Database

Saved as a user_cards row

With a stable card ID, the tool versions it uses, and audit details (who, when, tokens, latency).

Dry-run resultWhat happens
Valid query, rows returnedSave the card
Valid query, zero rowsSave the card and show an empty state. Zero waiting orders is a correct answer, not a broken card.
Binding does not resolveReject, or use the one repair attempt
Query failsReport the error. Never treat it as empty data.
Timeout or row limit hitFail safely and say which limit was hit
Optional field is nullAllowed when the output schema marks it optional or nullable. Only required fields count as broken.

3.2 Showing and using a card (/api/tool)

Browser · Renderer

Each Query() calls /api/tool

Through the query cache, so two cards asking for the same data make one request.

Server

Session → role check → schema check → handler

The handler gets ctx from the session and returns only this store's rows. Output is checked against the output schema and size-capped.

Browser

Filters, refresh and buttons

Go straight to /api/tool. No AI call, so they are fast and cost nothing. A write declares what it invalidates, and every card that reads that data refetches.

What a layout looks like

root = Stack([tbl])
q = Query("get_store_orders", {olderThanDays: 2},
      {"orders": []})          // empty while loading
tbl = Table([Col("Customer", q.orders.customer),
             Col("Status",   q.orders.status)])

How a hand-written page changes data

m = Mutation("update_order_status",
      {orderId: $order, status: $status})
btn = Button("Save",
      Action([@Run(m), @Run(q)]))  // save, then refresh

If @Run(m) fails, the next steps are skipped. AI-made cards may not contain Mutation.

4 · What is stored where

Shared role pages, personal rows on top

Nobody gets a full copy of a page. Admin changes to a role page reach every user, and a user's own cards and changes are separate rows.

TableHoldsKeyed by
page_layoutsThe role's default page as OpenUI Lang, with a versionrole + page
user_cardsCards the user asked for: layout text, position, size, pinned, hidden, tool versions used, versionuser + page + stable card_id
user_page_prefsWhich default blocks the user hid or moveduser + page
ui_stateSaved screen state as JSON: page date range, a card's filter or sortuser + scope (page:orders or card:<id>)
sessionsRandom session ID, user, expirysession ID
audit_logActor, tool or ask, outcome, latency, tokens. No full payloads.time + user
GoCart tablesProducts, orders, cart, addresses. Layouts never contain data rows.store / user

Reset to default

Deletes the user's user_page_prefs rows. Their own cards stay unless they remove them.

Two open tabs

Layout and card saves send the version they started from. A stale save is rejected instead of silently overwriting. Screen state uses last write wins.

Building blocks

OpenUI's built-in components with GoCart's colours to start. A generated spec tells the server what exists. GoCart's own components can be registered later.

5 · Sessions & user state

Who the user is and how their screen state is kept

OpenUI keeps screen state in memory per Renderer and gives us onStateUpdate and initialState. It has no session store, so we build one.

5.1 Who is the user?

User logs in. The server creates a sessions row.

The browser gets a cookie holding only the session ID: HttpOnly, Secure, SameSite=Lax.

Every request builds ctx from the cookie. POSTs also pass a CSRF check.

5.2 Browser cache rules

  • Query keys include the user ID: [userId, tool, args].
  • Logout and account switching clear the whole cache.
  • Nothing renders until the new session has loaded, so the previous user's data never flashes.
  • The server's checks stay authoritative whatever the cache holds.

5.3 Card state

The user changes a filter. OpenUI calls onStateUpdate. We wait 400 ms, then save to /api/state, and also save on tab close with sendBeacon. The next visit passes it back through initialState.

5.4 Page-wide state

The date range lives in a small client store and is saved to /api/state. Cards pass it into their query args, so changing it refetches every card. It is not a tool.

5.5 Refreshing after a write

A write tool declares invalidates: ["orders"]. The cache refetches every query whose tool reads orders, including the cart badge in the React header. Other tabs: add BroadcastChannel in production.

6 · Demo vs production

Disposable demo, not an insecure one

We build for the GoCart demo first. Infrastructure the demo does not need can wait. Tenant isolation, safe execution and correct data handling cannot.

Day one

In the demo from the start

  • Session-derived ctx and store-scoped repository functions
  • Tool registry with zod input and output schemas
  • Registered components only; server-side validation
  • Read-only AI cards
  • Tool timeouts and row limits
  • Dry run with the result rules in 3.1
  • Cache keyed by user and cleared on logout
  • "Needs rebuild" fallback for broken saved cards
  • One repair attempt; token and latency logging
Deferred

Fine to leave out of the demo

  • Postgres (SQLite for the demo)
  • MCP adapter
  • Cross-tab refresh, optimistic updates
  • Schema migration tooling
  • Rate limits beyond a simple cap
  • Full audit log and dashboards
  • Registering GoCart's own components
Before real customer data

Must be finished first

  • Postgres with row-level security per store
  • Rate limits on /api/ask and /api/tool
  • Full audit log with retention rules
  • Schema versioning with a rebuild workflow
  • CI that re-checks every saved layout on tool changes
  • Agreed LLM provider terms and a monthly budget
  • Security review of the session and tool paths

8 · Decisions for the call

Nine things to agree on

1

How do layouts reach the data?

Recommended: browser → /api/tool → tool registry, all inside the app. MCP as an optional adapter from the same registry.

2

Demo or production first?

Recommended: demo first, with the day-one list in section 6. Nothing reaches real customer data until the right-hand list is done.

3

Which pages first?

Recommended: Seller → Orders as the slice, then seller and admin pages. Shopper pages later because of SEO, brand and checkout risk.

4

What stays plain React?

Recommended: routing, header, login, payment and image upload. Page bodies become OpenUI.

5

Can the AI write layouts that change data?

Recommended: no. Enforced by the validator. Any future AI-made writes need a separate permission and confirmation flow.

6

Who can change pages?

Recommended: each user adds cards and hides or moves blocks for themselves. An admin changes the role default for everyone.

7

Which components?

Recommended: OpenUI's built-ins with GoCart's colours to start.

8

Which model and keys?

Open: Gemini (used in the POC) or Claude. We need an API key and a monthly budget.

9

Which database?

Recommended: SQLite for the demo, Postgres with row-level security for production.

9 · Other ways we considered

Options we looked at and why we did not pick them

Product approach

Overlay on top of the existing app, no migration

Keep for locked apps
Why not
OpenUI draws new UI where we place it. It cannot change the app's existing parts, and hiding old parts with CSS selectors breaks when the markup changes.

Browser extension

Not picked
Why not
Every user must install it, the app's owner has no control, and it breaks when the markup changes.

Dashboard builder without AI, or a separate low-code tool

Not picked
Why not
Users can only pick widgets someone already built, or must use a second app with a second login.

What the AI produces

AI writes raw HTML or React

Not picked
Why not
Free-form code cannot be checked reliably before it runs and can carry scripts. OpenUI Lang is small and checked on the server.

Send the data to the AI

Debug switch only
Why not
Customer data would leave our system, and the AI could type numbers into the card instead of binding them.

Generate the page on every visit, or stream it in

Not picked
Why not
Slow, costly, different each time, and a streamed card cannot be validated and saved as a whole.

How data is reached

Separate MCP server in the path of every page load

Later, as an adapter
Why not
The AI only reads tool schemas; it never calls tools. A separate server adds a network hop and a second auth layer between the app and the tools, with no gain for the pages.
Keep for
Outside agents. Generate it from the same registry so the checks are identical.

Browser calls the app's functions directly

Prototype only
Why not
No single place for login checks and logs.

How user changes are stored

Full copy of the page per user on first change

Replaced in revision 2
Why not
The copy goes stale. Users never get later changes to the role page, and every copy breaks separately when a tool changes.

Page-wide state as a server tool

Replaced in revision 2
Why not
Other cards would not know to refetch, and it mixes screen state with business data. A client store saved to /api/state does both jobs.

Only in-memory state, or everything in localStorage

Not picked
Why not
Lost on reload, or stuck on one device. localStorage is used only for small preferences such as the Ask button position.
10 · Risks and things still to check

What could go wrong

RiskWhat we do about it
One store seeing another's datactx from the session only, store-scoped repository functions, ownership checks on every ID, tests in phases 6 and 18. Row-level security in production.
Previous user's data on a shared browserCache keyed by user and cleared on logout or switch; nothing renders before the new session loads.
AI reliability unknownThe POC never recorded a success rate. Phase 20 measures one before we promise anything.
Made-up numbers in cardsValidator rejects hard-coded values in data components; test questions in phase 20 try to provoke it.
Tools change and break saved cardsCards record tool versions; broken cards show "needs rebuild"; CI re-checks saved layouts before production.
Cost per questionSend only the role's tools and a trimmed component list; log tokens per request. The full component list is estimated at about 10,000 tokens, still to be measured.
Shared state between RenderersNot verified whether two Renderers can share a $variable. The client store in 5.4 does not depend on it.
Next.js versions differGoCart uses 15.3.5, the POC uses 16. Agree one version in phase 3.
